# README

README は、初めて開いた読者が「これは何か」「どう動かすか」「どう貢献するか」「困ったらどこを見るか」を、本文とリンクから辿れる入口です。配置階層ごとに読者と責務が異なるため、単一の README の構成をすべての階層へコピーしません。

## 種類と責務

| 種類 | 配置例 | 主な読者 | 主な目的 |
| --- | --- | --- | --- |
| ルート README | `/README.md` | 初めてリポジトリを開く人、新規メンバー | プロジェクト全体の概要と入口を示す |
| アプリ／サービス README | `/apps/<name>/README.md`、`/services/<name>/README.md` | そのアプリを開発・運用する人 | 単体で動かす手順とシステム内の役割を示す |
| パッケージ README | `/packages/<name>/README.md` | ライブラリの利用者 | 配布物の導入方法と公開 API を示す |
| docs README | `/docs/README.md` | ドキュメントを探す人 | 個別文書への目次と追加ルールを示す |

そのディレクトリが単体で build または実行できる成果物なら、アプリ／サービスまたはパッケージ README を置きます。複数の成果物や設定をまとめるだけのディレクトリなら、親の README が全体を説明し、子 README は必要なときだけ追加します。

## 共通ルール

- 環境変数は各アプリやパッケージの `.env.example`、設定 schema、起動処理などを source of truth とし、README には値を書かず、必要な変数名と安全な導線だけを示します。
- コマンドと version は `Taskfile`、`package.json`、`mise.toml`、lock file、CI 定義など実際の定義を参照します。README に一覧を書く場合も、定義ファイルとの対応を保ちます。
- リポジトリ内の文書には配置に耐える相対リンクを使い、配布物で相対リンクが使えない場合だけ公開 URL を選びます。リンク先の存在と公開範囲を確認します。
- 削除済みの機能、非推奨の手順、過去の状態を現在の使い方として残しません。履歴を残す必要がある場合は CHANGELOG や release note の正本へ移します。
- コード例は現在の公開 API、必要な import、入力条件、期待結果と一致させ、未実行なら実行済みと表現しません。credential、token、個人情報、内部 URL は安全な placeholder に置き換えます。
- README に開発の branch、commit、Issue、PR の規則を定義せず、必要な場合は [git-workflow](../../../../coding-workflow/skills/git-workflow/SKILL.md) の該当 reference へリンクします。

## ルート README

次の順序を基本にし、該当しない項目は無理に作らず、代わりに適切な導線を示します。

1. プロジェクト名と一行説明。何を提供し、誰が使うかを明記します。
2. 概要と現在のスコープ。目的、背景、現在対応している範囲を数行で示します。
3. リポジトリ構成。monorepo なら主要なアプリ、サービス、パッケージ、docs の役割と README への相対リンクを示します。
4. 動作環境。対応 OS、必要な runtime、外部サービス、ローカルで必要な依存を source of truth と一致させます。
5. 全体セットアップ。clone から `mise install`、`pnpm install` など、実際のプロジェクトで必要な準備を上から実行できる順序で書きます。
6. よく使うコマンド。workspace 横断の task と目的を示し、個別アプリ固有のコマンドは子 README へ委ねます。
7. トラブルシューティング。全体セットアップや起動で起きやすい失敗と、確認すべき source of truth を示します。
8. 外部リンク。CONTRIBUTING、上位 docs、運用 dashboard、Notion／Confluence など、読者が次に進む正本を案内します。

ルート README には、個別アプリの endpoint 一覧、内部 API の詳細、ソースから読める関数一覧、クラス図を詰め込みません。必要な情報はアプリ README、API 仕様、生成ドキュメントなど本来の責務へリンクします。

## アプリ／サービス README

そのアプリだけを開発・運用する読者が、ルートの準備を前提にして作業できる構成にします。

1. アプリ名と一行説明。システム全体で担う役割を示します。
2. アーキテクチャ上の位置。依存するアプリ／サービス、呼び出す側と呼び出される側の関係を示します。
3. 固有の動作環境。runtime、外部依存、ローカルサービスを示します。
4. セットアップ。このアプリだけを触る人が実行する準備を示し、ルートで済む手順は重複させません。
5. 起動方法。開発モード、本番相当モード、container 起動など実際に使う入口を示します。
6. 使い方の入口。Web の URL、CLI の entry command、API の OpenAPI や endpoint 一覧へのリンクを示します。
7. ディレクトリ構成。主要ディレクトリの責務と関連 README を示します。
8. コマンド一覧。`package.json`、`Taskfile`、`mise.toml` などで定義された task の目的を示します。
9. 環境変数。このアプリが読む変数名、必須／任意、用途、既定値または未設定時の扱いを示し、実値は書きません。
10. テスト実行方法。unit、integration、E2E の分類と、source of truth である実行方法を示します。
11. トラブルシューティング。このアプリ固有の失敗、ログの場所、確認すべき設定を示します。
12. デプロイと運用。本番への動線、監視 dashboard、on-call runbook、rollback の正本へリンクします。

## パッケージ README

社内または公開 registry に配布したときにも読めるよう、次を含めます。

1. パッケージ名と一行説明。
2. インストール方法。`npm i <package>`、`uv add <package>` など、対象 registry の認証が必要ならその導線を示します。
3. 最小の使用例。source の公開 API と一致し、利用者がそのまま試せるコードを記載します。
4. 公開 API。型、引数、戻り値、例外、詳細ドキュメントへのリンクを示します。
5. 対応 version。Node.js、Python などの runtime 下限を実定義と一致させます。
6. 変更履歴。CHANGELOG または GitHub Releases の正本へリンクします。
7. 貢献方法。リポジトリの CONTRIBUTING と、必要な review 導線へリンクします。registry 表示でも切れない形式を選びます。

## docs README

`docs/README.md` は目次に徹し、個別文書の内容を重複させません。対象範囲、各文書への相対リンクと一行説明、命名・配置・レビュー導線など追加時のルールを示します。
