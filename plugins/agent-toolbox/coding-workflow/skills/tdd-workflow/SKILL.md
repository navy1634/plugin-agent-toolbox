# TDD Workflow

新しい機能、バグ修正、リファクタリングなど、利用者から見える振る舞いを変更する作業で使います。仕様と受入条件をテスト可能な契約へ変換し、テストを先に作って失敗理由を確認してから、最小限の実装と検証を進めます。

## 基本契約

- テストは公開された入力、出力、状態、エラー、外部との境界など、利用者または呼び出し元から観測できる振る舞いを検証します。private field、内部の呼び出し順、実装クラス名を契約にしません。
- テストコードは仕様、受入条件、既存のテスト規約だけを根拠にし、実装コードの現在の挙動へ依存させません。テストを通すために実装に沿った期待値やケースを作ると、実装が誤っていても通るため、テストを作成する意味が失われます。
- 仕様、受入条件、既存のテスト規約を共通の根拠にし、テストと実装で公開名、パス、引数・戻り値の型、入出力、外部境界を一致させます。どちらかが相手の実装やテストから契約を推測してはいけません。仕様と既存実装が食い違う場合は、テストを実装へ合わせず、仕様の差分または実装の不備として扱います。
- 振る舞いを変更する場合は、正常系だけでなく空値・境界値・不正入力・依存先障害・代替経路など、受入条件に必要なケースをテストへ落とします。
- fixture、mock、emulator はテストの独自契約を作るためではなく、必要な境界を分離して再現するために使います。テスト用の double に本番アルゴリズムを複製しません。

## 進め方

1. 仕様と受入条件を user journey または公開契約へ分解し、検証する振る舞いと対象範囲を決めます。
2. 実装前にテスト、fixture、必要な test double を作成します。テストが変更のない状態で失敗することを実行結果で確認し、失敗理由が契約の未実装部分を示していることを記録します。
3. RED のテストを満たす最小限のプロダクション実装を加えます。テストを弱めたり、実装に合わせて期待値を変えたりしてはいけません。
4. GREEN を確認した後、重複、命名、境界、性能などを改善します。REFACTOR 中も振る舞いを変えず、テストを再実行します。
5. 変更箇所だけでなく、影響を受ける unit、integration、E2E とプロジェクトが定める format、lint、型検査、coverage を実行します。タスクランナーがある場合はその経路を使います。
6. 実行したコマンド、対象範囲、環境、結果、未実行の検査と理由を分けて報告します。ローカルの成功を実環境やCIの成功と同一視しません。

テストランナーがない文書・設定変更では、作業指示に定義した静的検査をテスト相当の受入条件として扱います。理由のない skip、xfail、TODO で未検証部分を隠してはいけません。

## 完了条件

失敗理由が変更に対応する RED として記録され、テストと実装が共有契約に一致し、必要なテスト・静的検査・coverage・E2E が再実行済みであることを確認します。未実行の範囲や外部環境で未確認の事項がある場合は、完了扱いにせず明示します。
