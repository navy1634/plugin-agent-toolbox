# テスト設計

## 仕様からテストケースへ

仕様を「誰が、何を、なぜ行うか」という user journey、または公開関数・APIの契約に分解します。各ケースには、前提、入力、観測する結果、失敗時の期待、外部境界を記載し、テストと実装が同じ契約を参照できるようにします。

テストの期待値、ケース、公開名、引数、戻り値は仕様と受入条件から決めます。現在の実装を読んで通りやすい期待値へ寄せたり、実装の分岐をそのままテストケースへ写したりしてはいけません。実装と仕様が異なる場合、テストは仕様を示す失敗として残し、実装または仕様の変更を別途判断します。

一つの機能について、少なくとも次の観点を受入条件として検討します。

- 正常な入力が期待する結果を返すこと
- 空値、未指定、最小値、最大値、件数上限などの境界を扱うこと
- 型違い、不正形式、権限不足などの入力エラーを扱うこと
- DB、cache、外部API、ネットワークなどの依存先障害を扱うこと
- fallback、再試行、重複実行、部分的な失敗などの代替経路を扱うこと
- 認証・認可、個人情報、金銭、データ破壊など高リスクの結果を通常より厚く検証すること

たとえば検索機能なら、関連結果、空 query、上限件数、検索基盤停止時の fallback、順位付けを別々の振る舞いとして記述します。テスト数を増やすこと自体を目的にせず、受入条件に対応しない assertion は追加しません。

## 観測可能性と構造

テストは公開された入力、戻り値、HTTP status、response schema、永続化結果、発行イベント、画面上の結果などを検証します。private field、内部の call 順、実装クラス名、偶然のCSS classを固定しません。

Arrange、Act、Assert を分け、テスト名から検証する振る舞いが分かるようにします。一つのテストは一つの振る舞いに集中させますが、同じ振る舞いの結果を確認するために複数の assertion が必要な場合は分割しません。

テスト間でデータや外部状態を共有せず、各テストが自分の前提を作成・破棄できるようにします。fixture の scope は、共有しても独立性を損なわない場合だけ広げます。

## テスト種別の境界

- unit は一つの規則またはコンポーネントの振る舞いを、外部の実行環境から分離して検証します。
- integration は API endpoint、DB操作、cache、service 間の接続、transaction、response schema を、実際の境界に近い形で検証します。
- E2E はログイン、検索、作成、更新、決済など、利用者が入口から出口まで行う主要な journey を検証します。ブラウザ固有の手順は [Playwright](playwright.md) を参照します。

同じケースを全種別へ重複して追加せず、unitで規則、integrationで境界、E2Eで利用者経路を担わせます。外部サービスを本物へ接続する範囲は受入条件と環境の安全性から決め、ローカルのmock・emulator・recorded response・実環境の証拠を区別します。

coverage、テスト速度、並列実行、リトライ回数の目標はプロジェクト設定を正本とします。数値だけを満たすために無意味な assertion、広すぎる mock、理由のない skip を追加してはいけません。
