# 検証と完了判定

## 検証の順序

振る舞い変更では、実装前に追加テストのREDを確認し、実装後に次の順序で必要な範囲を検証します。

1. 変更対象のunit、integration、E2Eを実行し、テストが共有契約の振る舞いを確認していることを確かめます。
2. プロジェクトのtask runnerで、全体のtest、lint、format、type-check、coverageを実行します。
3. 影響する外部境界、ブラウザ、emulator、recorded response、CIなど、受入条件が要求する環境を確認します。
4. 失敗があれば、テスト、実装、fixture、設定、契約のどこが原因かを切り分けて修正し、該当する検証を最初から再実行します。

テストランナーのないMarkdown・設定変更では、作業指示に定めた構文、lint、schema、生成物の比較などの静的検査を同じ完了ゲートとして扱います。

## coverage と品質指標

coverage、テスト速度、並列実行、retry、許容するskipの条件はプロジェクト設定を正本とします。このskillから80%などの固定値を一律に要求しません。ただし、認証・認可、金銭、入力検証、データ破壊など高リスクの経路は、数値だけに頼らず境界と失敗を厚く確認します。

数字を満たすためだけのassertion、広すぎるmock、実装詳細への固定、理由のないskip・xfailは完了条件を満たしません。未検証の分岐を隠すためにcoverage設定を緩めません。

## 実行証拠の記録

完了報告には、実行したコマンド、成功・失敗、対象範囲、実行環境、coverage、生成したreportやアーティファクトの場所を記載します。単一テストのローカル成功、emulatorの成功、recorded HTTPの成功、stagingや実環境の成功、CIの成功は、それぞれ別の証拠として報告します。

E2Eの失敗では、browser／server log、入力、再現手順、スクリーンショット、trace、video、HTML/JUnit reportを必要な範囲で紐付けます。flakyを一時隔離した場合は、原因調査、issue、解除条件、CIへの影響を残し、隔離だけで合格にしません。

## 完了条件

- REDの失敗理由が変更の未実装部分または受入条件の不足を示していること
- テストの期待値とケースが仕様・受入条件から追跡でき、実装の現在の挙動へ合わせて作られていないこと
- テスト、fixture、mock、実装が同じ公開契約に一致していること
- 必要なテストとプロジェクト全体のDoDがエラーなしで完了していること
- coverage、lint、format、型検査、E2Eなど、該当する検証を省略していないこと
- skip、xfail、retry、外部環境の未確認範囲を理由とともに報告していること
- 実行結果だけでなく、未実行の検査と残るリスクを明示していること
