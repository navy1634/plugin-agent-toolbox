# 統合テストと E2E

## 統合テスト

統合テストは API endpoint、DB操作、cache、キュー、service 間の接続を検証します。HTTP status、response schema、入力エラー、認証・認可、transaction、依存先障害を確認し、単純なmockではなく実際のclientやemulatorに近い境界を使います。

外部境界ごとに、成功、タイムアウト、再試行可能な障害、恒久的なエラー、空の応答、部分的な応答を受入条件へ含めます。DBを使う場合はテストごとのtransactionまたはデータ初期化で分離し、実行順や共有データに依存させません。

integrationで確認した境界をE2Eへ重複して詰め込まず、integrationでは接続と契約、E2Eでは利用者がたどる結果を検証します。

## E2Eの対象とシナリオ

E2Eはログイン、検索、作成、更新、削除、決済など、失敗時の影響が大きい主要 journey を入口から出口まで検証します。各journeyについて、正常系、空状態、入力境界、権限不足、依存先障害、再読み込みや重複操作を必要な範囲で定義します。

画面の見た目ではなく、利用者が認識できる役割、label、名称、意味のある test id を入口にします。偶然のCSS class、DOM階層、描画順、固定位置だけに依存させません。動的な表示は固定時間のsleepではなく、対象の状態、URL、レスポンス、または利用者が確認できる結果を待ちます。

各テストは自分のユーザー、データ、認証状態を準備し、他のテストとブラウザ状態・DB状態・順序を共有しません。共有が必要な環境でも、読み取り専用の固定データと明示的な初期化手順に限定します。

## 失敗の再現と証拠

失敗時は、browser log、server log、ネットワーク情報、再現手順、入力データ、環境、対象テストを保存します。スクリーンショット、trace、video、HTML/JUnit report は、プロジェクトの実行設定に従い、失敗の原因を特定できる範囲で取得します。

ローカル、emulator、recorded HTTP、実環境、CIの証拠を区別し、ローカル成功だけで外部サービスやデプロイ済みシステムの動作を断定しません。flakyな失敗は、まず競合、非決定的データ、環境、待機条件、依存先の遅延を調査します。リトライや一時的な隔離は失敗を隠すために使わず、原因、issue、解除条件、適用範囲を残します。

watch mode は開発中の調査に限り、完了判定には使いません。完了時はタスクランナー、coverage、CI、E2Eの実行結果と対象範囲を分けて報告します。Playwrightの具体的な構成、locator、POM、実行例は [Playwright](playwright.md) を参照します。
