# Test doubles と fixture

## 目的と境界

fixture、mock、stub、spy、fake、emulator、recorded response は、テスト対象と外部境界を分離し、受入条件に必要な応答や障害を再現するために使います。テスト専用の別契約を作ったり、プロダクションのアルゴリズムを double に複製したりしません。

DB、cache、外部API、キュー、ファイルシステム、時刻、環境変数など、テストの決定性や安全性に影響する境界を明示します。公開契約に必要な応答・例外だけを設定し、private state や実装内部の call 順を直接差し替えません。

サービス固有の client に近い mock または emulator がある場合はそれを優先します。AWS SDKを使うテストでは、都合のよい戻り値だけを返す自作fakeを作らず、`moto.mock_aws` のようなサービスエミュレーターと実際のclientを使います。ad-hoc な `FakeXXXX` クラスは、選択したmock・emulatorでは再現できない振る舞いを狭く表す場合だけ使い、必要な理由を記録します。外部サービスを本当に呼ぶテストは、認証情報、データ破壊、費用、環境の隔離を確認した受入条件に限定します。

## fixture の設計

- fixture の scope はテスト間の独立性を保てる最小範囲にします。
- テストごとに入力データと外部状態を初期化し、後続テストが実行順へ依存しないようにします。
- fixture はテストの準備と後片付けに集中させ、検証対象の業務ロジックを実装しません。
- 複数のテストで同じfixtureを使う場合も、変更可能なオブジェクトやリストを共有しません。
- 認証情報や本物の秘密値をfixture、recorded response、ログ、アーティファクトへ書き込みません。

契約上の意味のある値が不要な場合は、次の型に応じた最小値を使います。入力制約が定義されている場合だけ、制約を満たす最小の有効値へ置き換えます。

| 型 | 基本値 |
| --- | --- |
| `str` | `""` |
| `int`、`float` | `0` |
| `bool` | `False` |
| list系 | `[]` |
| dict系 | `{}` |
| nullable | `None` |

型または制約が契約から分からない場合は、実装を推測して値を決めず、契約の不足として戻します。

## mock と emulator の使い分け

mock は呼び出し先の成功・失敗・応答を制御し、対象の公開結果を検証するために使います。mockの呼び出し回数や引数は、公開契約が要求する場合に限って検証します。内部実装を固定するためだけの `assert_called_once` を追加しません。

emulator は、transaction、schema、serialization、権限、サービス固有のエラーなど、単純なmockでは再現できない境界を検証するときに使います。emulatorの挙動と実環境の挙動が一致しない範囲は、検証報告で明示します。

DBを扱うrepository自身のテストは、原則としてin-memory DBや自作repository fakeで代替せず、Testcontainersで本番と同じDBエンジンを起動して実際のドライバーから検証します。SQL、transaction、schema、制約、index、DB固有の型や関数を含む契約も、実DB境界で確認します。本番DBがin-memoryまたはSQLiteそのものであるなど、代替が実態と一致する場合だけ例外とし、理由を記録します。単純な業務ロジックのunitではrepository interfaceをmockできますが、repository自身のテストでは実DB境界を省略しません。

recorded response を使う場合は、取得元、取得日時、マスキング状態、再生成手順を管理し、古い契約を無期限に正本として扱いません。外部仕様が変わったときに失敗して更新を促せるようにします。

## 変更後の確認

test double の変更でテストが通っても、対象の公開結果が変わっていないかを確認します。mockが複雑になった、fixtureの初期化に複数の条件分岐が必要になった、実装と同じ計算を再現し始めた場合は、テスト設計または契約へ戻して境界を見直します。
