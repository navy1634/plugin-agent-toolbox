# Pull Request

## 作成前の確認

全コミットを確認し、base branch との差分を git diff <base>...HEAD で読む。変更対象、互換性、移行、rollback など、差分から判断できる変更内容を整理し、既存の未コミット差分を PR の変更として混ぜない。

既存の PR 本文を更新するときは、現在の本文、template、PR の head と base、全コミット、差分を確認する。
差分に含まれるだけの付随変更を PR の主題にせず、目的と受け入れ条件に結び付く変更を選ぶ。
変更内容は実際のファイルや設定から裏付ける。

レビューを依頼する前に、作成者が必要なローカル検証と最新 head の必須 CI を実行・確認し、失敗や未完了があれば解消する。確認できる事実や検証作業をレビュワーへ委ねず、必要な検証が残ったままレビューを依頼しない。

## タイトル

タイトルは 30 文字未満の一行で、単一の変更を表す。ファイル名、実装理由、検証結果、複数の変更をタイトルへ詰め込まない。

## template の優先順位と定義

既存の .github/PULL_REQUEST_TEMPLATE.md、ロケール別 template、または .github/PULL_REQUEST_TEMPLATE/ の選択対象がある場合は、それが PR 本文の正本である。見出し、順序、必須欄、checkbox、記法を template のまま使い、ここで定義する fallback 構成で置き換えない。複数種類の PR を扱う場合は、変更内容に合う既存 template を選び、作成時に ?template=<name>.md で指定する。

template が存在しない場合だけ、後述の fallback 構成を使う。template を新設する場合も、既存の repository 文書と運用を確認したうえで、この fallback 構成を初期案にする。

```markdown
## 概要
<!-- 何をなぜ変えたかを 2〜3 行 -->
## 変更点
<!-- 振る舞い、API、設定、データへの影響 -->
## 設計・影響
<!-- 変更の判断理由、互換性・移行・ロールバックへの影響 -->
## 関連 Issue / ADR
<!-- 関連する Issue や ADR がある場合だけ記載 -->
```

template を新設・変更した場合は見出しの責務、checkbox の意図、既存 locale との整合性、参照先のリンクを確認する。既存 template の内容を generic な fallback 構成へ寄せる判断は、現在の依頼に変更理由と対象が明記されている場合だけ行う。実際の PR 本文は template の欄へ記載し、template の形式と本文の記載規則を別の skill に分散させない。

template の見出し、順序、checkbox 形式は維持するが、欄の有無にかかわらず PR 本文へ現在の状態や進捗を書かない。template が未確認事項、検証状況、レビュー担当者への確認依頼を求める場合も、それらを本文へ書かず、必要な確認を完了してからレビューを依頼する。template 自体の変更が必要なら、PR 本文とは別に扱う。

template がない場合の本文は、次の fallback 構成で欄ごとの責務を分ける。

| 欄 | 記載する内容 | 記載しない内容 |
| --- | --- | --- |
| 概要／Summary | 何を変えたか、なぜ必要かを 2〜3 行で記載する | ファイル名、詳細な変更一覧、作業の進捗 |
| 変更点／Changes | 振る舞い、API、設定、データ、互換性への影響を具体的に記載する | 概要の繰り返し、実行・検証・デプロイの状態 |
| 設計・影響／Design and impact | 変更の判断理由と、差分から判断できる互換性・移行・rollback への影響を記載する | 未確認事項、未解決の検証、レビュワーに委ねる確認作業 |
| 関連 Issue / ADR | 判断や要件の正本へ辿るための参照を記載する | 現在の状態を説明するためだけのリンク |

template がない場合も同じ欄を使う。検証結果、CI の状態、未確認事項、未解決事項、進捗、レビュー依頼は PR 本文に含めない。検証結果は CI や検証ツールで確認し、作成者の完了報告は PR 本文と分ける。

## 本文の書き分けと更新

既存 template の欄名と順序を優先し、各欄の役割を次のように判断する。
概要には変更の対象、主な振る舞い、目的を、PR を開いた人が本文の続きを読むべきか判断できる具体性で書く。
詳細には、レビューに必要な変更の仕組みと影響を整理する。
概要を変更一覧や実行ログで埋めず、詳細を抽象的な見出しだけで済ませない。
文体、箇条書きの句読点などは、会話ではなく対象の本文に対するユーザーの指定と既存 template に合わせる。

検証結果、workflow や job の状態、未実行・未確認の範囲、マージ後の確認予定は PR 本文へ記載しない。作成者はレビュー依頼前に必要な検証を終え、最新の差分と CI を確認する。
レビューでは差分に基づく設計判断を依頼し、作成者が確認できる事実、権限、実環境、別件の障害調査などの確認作業をレビュワーへ依頼しない。必要な確認を完了できない場合はレビュー依頼を保留し、状況は依頼者への完了報告など PR 外で伝える。

ユーザーが本文を修正した場合は、その変更を新しい要件として全欄に反映する。
remote へ更新する直前に現在の本文と手元の下書きを再取得・比較し、自分以外の変更を保持する。
本文全体を書き戻す場合は、今回意図した差分だけになっていることを確かめ、更新後に remote の本文と head を読み直す。
一つの指摘に対応するたびに一文だけを直して終えず、累積した要件、欄の役割、事実関係を本文全体で確認する。
