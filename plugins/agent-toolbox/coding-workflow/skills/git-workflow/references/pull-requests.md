# Pull Request

## 作成前の確認

全コミットを確認し、base branch との差分を git diff <base>...HEAD で読む。変更対象、互換性、移行、rollback、実行した検証、未実行の検証を整理し、既存の未コミット差分を PR の変更として混ぜない。

## タイトル

タイトルは 30 文字未満の一行で、単一の変更を表す。ファイル名、実装理由、検証結果、複数の変更をタイトルへ詰め込まない。

## template の優先順位と定義

既存の .github/PULL_REQUEST_TEMPLATE.md、ロケール別 template、または .github/PULL_REQUEST_TEMPLATE/ の選択対象がある場合は、それが PR 本文の正本である。見出し、順序、必須欄、checkbox、記法を template のまま使い、ここで定義する fallback 構成で置き換えない。複数種類の PR を扱う場合は、変更内容に合う既存 template を選び、作成時に ?template=<name>.md で指定する。

template が存在しない場合だけ、後述の fallback 構成を使う。template を新設する場合も、既存の repository 文書と運用を確認したうえで、この fallback 構成を初期案にする。

```markdown
## 概要
<!-- 何をなぜ変えたかを 2〜3 行 -->
## 変更点
<!-- 振る舞い、API、設定、データへの影響 -->
## 動作確認
- [ ] 実行したコマンドと結果
- [ ] 関連 Issue: #
## その他
<!-- 制約、移行、ロールバック、レビュー観点 -->
```

template を新設・変更した場合は見出しの責務、checkbox の意図、既存 locale との整合性、参照先のリンクを確認する。既存 template の内容を generic な fallback 構成へ寄せる判断は、現在の依頼に変更理由と対象が明記されている場合だけ行う。実際の PR 本文は template の欄へ記載し、template の形式と本文の記載規則を別の skill に分散させない。

template がない場合の本文は、次の fallback 構成で欄ごとの責務を分ける。

| 欄 | 記載する内容 | 記載しない内容 |
| --- | --- | --- |
| 概要／Summary | 何を変えたか、なぜ必要かを 2〜3 行で記載する | ファイル名、詳細な変更一覧、検証結果 |
| 変更点／Changes | 振る舞い、API、設定、データ、互換性への影響を具体的に記載する | 概要の繰り返し |
| 動作確認／Test plan | 実行したコマンド、対象、結果、未実行の検証を記載する | 未実行の検査を成功したように書くこと |
| その他／Notes | 既知の制約、移行、監視、rollback、レビューで判断してほしい点を記載する | 変更点や検証結果の重複 |

template がない場合も同じ4欄を使う。template に欄がある事柄を概要へ重ねず、headline と詳細、検証結果、レビュー上の注記をそれぞれ対応する欄へ振り分ける。未実行の検査を成功したように書かない。
