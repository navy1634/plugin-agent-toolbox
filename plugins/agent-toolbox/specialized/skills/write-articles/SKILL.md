# 記事作成

会話と作業ログから確認できる事実、決定事項、手順、検証結果だけを抽出し、読者が再現できる記事へ変換する。媒体固有の形式は対応する reference を読み、共通の執筆・公開契約はこの skill に従う。

## 適用条件

技術記事、作業記録、障害対応、設計判断、チュートリアル、既存記事の更新を作成または公開するときに使う。単なるメモや、根拠のない経験談の創作には使わない。

## 開始時の確認

1. 対象媒体と投稿先 repository、更新対象の記事、公開範囲が依頼で明示されているか確認する。投稿先を特定できない場合は directory や repository を勝手に作らず停止する。
2. 投稿先の現状、既存記事、未コミット差分、管理元、生成手順、検査設定を読み、既存記事を上書きしない。
3. 読者、記事の目的、前提知識、公開後に読者ができるようになることを一文で定める。
4. 会話、URL、ファイル、コマンド出力、テスト結果から根拠を収集し、確認済みの事実・推測・提案を分ける。
5. 媒体固有の配置、front matter、CLI、公開フラグは対応する reference を読み、プロジェクトで有効な command と設定を正本にする。

## 本文の構成

記事は次の順序を基本にし、内容に不要な章は理由を明示して省きます。

1. タイトルと概要。何を扱い、読者にどんな価値があるかを短く示す
2. 背景と問題。なぜこの作業が必要になったかを、確認できる事実で説明する
3. 前提。対象 version、環境、依存、読者が済ませる準備を示す
4. 結論または採用した方針。重要な判断を先に示す
5. 手順または実装。上から再現できる command、設定、コード例を載せる
6. 判断理由。選択肢、不採用理由、トレードオフを区別して説明する
7. 検証結果。実行した検査、対象、結果、証拠の範囲を記載する
8. 制約と注意点。未検証、環境差、残るリスク、ロールバックを隠さない
9. 次の行動。読者や運用者が続けて行うことを示す

掲載する数値、効果、仕様、経験談、command、URL は会話または対象 repository で確認できるものだけにする。外部情報を補うときは一次情報をリンクし、引用元と本文の対応を明示する。コード例は最小で実行可能にし、secret、個人情報、内部 URL、推測で作った値は安全な placeholder に置き換える。複数媒体へ投稿する場合も本文を機械的に複製せず、事実と検証結果だけを一致させる。

## 公開の扱い

明示的な公開依頼がない限り下書きとして作成する。公開前に、対象 repository、公開先、認証情報、branch、CI／連携設定、公開範囲、既存記事の更新か新規作成かを確認する。`git push`、外部サービスへの投稿、公開フラグの変更、公開予約は依頼の対象に明記された場合だけ行う。

公開を実行した場合は、公開先の URL、公開状態、反映された version、CI／連携結果を確認する。ローカルのファイル作成や lint 成功だけで公開完了とは扱わない。

## 完了条件

記事が対象媒体の形式と配置に適合し、タイトル・概要・本文・公開状態が一致していることを確認する。根拠のない主張、秘密情報、内部推論、未確認の command がなく、本文の構成、リンク、コード例、媒体固有の front matter、markdownlint／textlint、公開前受入条件を検証済みであることを完了条件とする。未検査や rule 未導入が残る場合は完了と報告しない。

完了報告には作成・更新ファイル、対象媒体、採用した要点、公開状態、実行した検査 command と結果、CI／外部連携の未確認事項、ユーザーの操作が必要な残作業を記載する。
